## 本批交付目标

玩家可以取消一个等待格中的全部菜品，原材料准确回到餐厅仓库，剩余队列顺序不变并自动向左补位，空闲锅继续领取下一份可制作菜品。

| 内容 | 计划行为 |
| --- | --- |
| 取消入口 | 非空且可取消的等待格右上角显示 ×；空格、锁定预览格不显示；沿用现有 UI 素材与布局 |
| 整格取消 | 一次清除该格当前所有等待份数，不影响其他格；若其中部分已下锅，仅处理格内剩余份数 |
| 准确退款 | 按每份菜实际预留的原材料退回餐厅仓库，不按取消时的菜谱重新计算，不退到背包 |
| 即时反馈 | 更新仓库数量、菜谱材料与可制作状态、格内数量；提供简短取消反馈，操作不等待动画完成 |
| 队列补位 | 保持剩余菜品的先后顺序，取消后空位向左压缩；继续复用原有空闲锅调度 |
| 重复操作保护 | 同一批次取消只能生效一次；旧按钮事件不取消补位后占据同一格的另一批菜 |
| 飞行中操作 | 尚未完成投料的订单保持独立身份；取消已有格不误退飞行中的材料，飞行结束重新判断入队条件 |

本批建议不增加二次确认弹窗。整格材料可完整退回，取消是可恢复操作；如最终包含锅内损耗式取消，需重新评估。

## 实现顺序

### 1. 保存每份订单的材料记录

当前 `CookQueueStackEntry` 只有菜谱和数量；入队后预留记录立即提交，无法可靠处理后续退款。将队列扩展为持有稳定批次身份及逐份材料凭据的记录，堆叠数量由实际订单记录维护。

建议沿用第一批的材料预留服务：飞行中与等待中均占用材料；进入等待队列时移交凭据所有权，真正下锅成功时才提交消耗，取消时返还。界面可用库存仍在点击制作时减少。失败退款、关闭组件的处理必须区分“飞行中”和“已经排队”，避免退款后菜品还留在队列。

### 2. 取消与下锅使用同一套订单状态

提供单一业务入口，先核验批次身份与状态，再取消整格或下锅其中一份。两种操作互斥，不能同一份菜既退款又开锅。退款使用冻结记录；即使同格各份菜的实际成本不同，也逐份准确返还。

补位和已有槽数变化逻辑一起维护订单凭据。现有缩容逻辑会警告并丢弃尾部条目，需改为明确处理无法保留的订单及材料，避免新增可退订单后出现无主预留。此项是数据一致性保护，不引入新的升级规则。

### 3. 接入取消按钮与反馈

在现有 `DishQueueSlot` 和真实餐厅队列布局中接入 ×。按钮绑定批次身份，而非仅保存槽位索引；刷新、补位和重复开关界面时正确更新绑定。复用现有美术和反馈组件，适配 1280×720、1920×1080、2560×1440，防止按钮遮住菜品数量。

### 4. 联调与验收

先验证材料守恒和状态转换，再在真实餐厅中验证按钮、下锅、飞行与界面刷新。保留第一批的转存和退款回归。

## 关键验收案例

1. 同格排入 3 份，每份消耗 2 个蘑菇；点击 × 后格子清空，仓库准确增加 6 个。
2. 上例已有 1 份下锅，只剩 2 份等待时取消，退款 4 个；若本批采用仅等待可取消方案，锅内菜继续制作。
3. 等待队列为 A、B、C，取消 B 后变成 A、C，顺序不变；取消 A 后空闲锅正常接手后续队首。
4. 两份同类菜分别按 2 个和 3 个材料入队，取消整格返还 5 个，后续修改菜谱不影响退款。
5. 重复提交同一取消请求、快速连点或按钮补位时，不重复退款、不误取消其他批次。
6. 点击取消时恰好有空闲锅取菜，材料数量和开锅份数保持一致，无免费制作或材料丢失。
7. 同类新订单仍在飞行时取消已有等待格，退款仅覆盖已取消订单，新订单随后正常入队或失败退款。
8. 菜单、仓库与队列数量即时一致；关闭再进入餐厅没有重复事件、空按钮或无主材料预留。
9. 继续通过第一批的进店转存、重复进出、入队失败、组件禁用及地牢库存隔离回归。
